# Registro de decisiones

Fecha de las decisiones iniciales: 2026-11-17.

| # | Decisión | Motivo |
|---|---|---|
| 1 | Arquitectura cliente-servidor con API central | Evita corrupción por escrituras concurrentes, centraliza reglas (un registro activo por empleado) y hora única |
| 2 | .NET 8 / C#, WPF para panel y admin | Liviano, nativo en Windows, sin navegador; el usuario delegó la elección |
| 3 | SQLite (WAL) vía API, migrable a PostgreSQL | Carga baja (30+ usuarios, latidos cada 30 s); simple de respaldar. A confirmar según SO del servidor |
| 4 | Admin como programa de escritorio aparte | Pedido del usuario; mantiene el panel mínimo y separa permisos |
| 5 | Identificación por nombre + PIN | Pedido del usuario; admin asigna PIN inicial, el empleado lo cambia |
| 6 | Cambio de obra pide confirmación | Pedido del usuario |
| 7 | Inactividad **2 horas** (antes 15 min; cambiado por el usuario el 2026-11-19); al volver se pregunta descontar/contar | Pedido del usuario (cubre almuerzo olvidado y lectura de planos) |
| 8 | Corte (apagado/cierre) se cuenta hasta el último latido | Pérdida máxima ~1 min |
| 9 | Doble registro: bloquear el nuevo | Pedido del usuario |
| 10 | Sin LAN: cronómetro local + sincronización idempotente | Evita pérdida de horas |
| 11 | Panel arranca con Windows en pausa, pide PIN | Nunca cuenta sin Play |
| 12 | Solo «obra» como dimensión (modelo extensible a tarea) | Pedido del usuario |
| 13 | Excel con horas decimales + hh:mm, sin redondeo | Pedido del usuario |
| 14 | Backup diario automático en el servidor | Pedido del usuario |
| 15 | Autoactualización del panel desde el servidor | Evita instalar PC por PC |
| 16 | Roles: Empleado + Administradores (cuentas propias) | Pedido del usuario; permite auditoría por persona |
| 17 | Empleado ve resumen hoy/semana, solo lectura | Pedido del usuario |
| 18 | Excel: el servidor guarda los registros en su base y **regenera automáticamente un .xlsx** actualizado (cada pocos minutos) en una carpeta del servidor; además el admin puede exportar bajo pedido | Pedido del usuario (2026-11-18): quiere que todo termine en una planilla Excel. Escribir directo desde 30+ PCs en un mismo .xlsx se bloquea/corrompe |
| 19 | El panel se entrega como **un único .exe** (autocontenido, sin instalar .NET) para Windows 10/11 | Pedido del usuario; todas las PCs son Windows 10/11 |
| 20 | Distribución: el servidor publica una página de descarga (ej. `http://IP:8080`) con el .exe del panel | Elegido por el usuario; facilita la autoactualización |
| 21 | Red: las PCs están conectadas por **wifi** (misma red local). Las caídas de conexión son más probables, por lo que el modo offline y la sincronización idempotente son críticos | Aclaración del usuario (2026-11-18) |
| 23 | Servidor en `src/Play.Server` (ASP.NET Core minimal API, EF Core + SQLite WAL, instalable como servicio de Windows). Sesiones de empleado guardadas en la base (sobreviven a reinicios del servidor, 24 h renovables) | Implementación Fase 1 (2026-11-18) |
| 24 | La base se crea con `EnsureCreated`. **Antes de producción hay que pasar a migraciones de EF Core**, porque `EnsureCreated` no modifica una base ya existente | Deuda técnica consciente |
| 25 | Cambio de obra = cerrar A y abrir B en una transacción; el inicio de B es el fin de A (sin huecos ni solapes) | Evita horas perdidas o duplicadas |
| 26 | Sincronización offline (`POST /api/registros/sincronizar`): idempotente por GUID; nunca descarta horas; solapamientos se guardan marcados `RevisarAdmin`; un registro «cortado» se extiende si el panel demuestra que trabajó más tarde; un registro corregido por admin no se pisa | Caídas de wifi |
| 27 | Accesos iniciales: PIN de 4 dígitos aleatorios y clave temporal del admin se escriben en `datos/accesos_iniciales.txt` junto al programa del servidor (entregar y borrar). Bloqueo de PIN: 5 intentos → 5 min | Seguridad básica sin enviar PIN por red |
| 28 | La carpeta de datos del servidor se llama `datos` (no `data`): en Windows `data` y `Data` son la misma carpeta y chocaba con el código fuente | Error encontrado en pruebas (2026-11-19) |
| 29 | El Excel automático es `datos/excel/horas.xlsx`, se regenera cada 5 min con todo el historial (archivo temporal + reemplazo). Si alguien lo tiene abierto en el servidor, se reintenta en el siguiente ciclo: abrir una copia o usar el reporte del admin | Pedido del usuario: Excel siempre al día |
| 30 | Los registros que cruzan la medianoche se reparten por día local en el Excel (zona America/Argentina/Buenos_Aires); horas decimales con 2 decimales + columna hh:mm con formato `[h]:mm` | Reportes por día correctos |
| 31 | Administración: cuentas propias con clave temporal obligatoria de cambiar (mín. 8 caracteres); toda corrección o alta manual exige motivo y registra una fila de auditoría por campo cambiado; no se corrigen registros abiertos | Trazabilidad |
| 32 | Backup diario con `VACUUM INTO` (copia consistente con usuarios conectados), verificado con `PRAGMA quick_check`. Se hace a partir de las 02:00 locales; si el servidor estaba apagado, se hace apenas arranca. Retención 30 días (siempre se conserva el más reciente). Carpeta por defecto `datos/backups`, configurable (`BackupDir`: conviene otro disco o carpeta de red) | Pedido del usuario: copia diaria automática |
| 33 | Página de descarga en `http://servidor:8080/`: lista los `.exe/.msi/.zip` de `datos/descargas` y los sirve por `/descargar/{archivo}` (solo nombres exactos de esa carpeta). Avisa del cartel de SmartScreen porque el .exe no está firmado | Distribución elegida por el usuario |
| 34 | El servidor se publica autocontenido (`scripts/publicar-servidor.ps1`, ~115 MB, no requiere .NET en la PC servidor) y se instala como servicio de Windows `PlayServidor` con `scripts/instalar-servicio.ps1` (no toca `datos` ni `appsettings.json` al actualizar). Regla de Firewall en todos los perfiles porque la red wifi suele estar como «Pública» | PC servidor aún sin definir; solo se asumió Windows x64 |
| 35 | La raíz de contenido del servidor es la carpeta del programa (`AppContext.BaseDirectory`), no el directorio desde el que se lanza | Evita perder la configuración al iniciarlo como servicio o desde otra carpeta |
| 36 | Panel en WPF, con la lógica separada en `Play.Client` (sin interfaz) para probarla contra el servidor real con una red que se puede «cortar» y un reloj controlable | Los casos límite son lo más riesgoso; ver `docs/PANEL.md` |
| 37 | Dirección del servidor: se escribe una vez por PC en el primer arranque (se valida con `/api/estado`); la página de descarga muestra qué escribir | El .exe es el mismo para todos y no se conoce la IP al compilarlo |
| 38 | Suspensión de la PC: un salto >90 s entre ticks de 1 s termina el registro en el último tick vivo | Evita contar las horas de una PC dormida |
| 39 | Si el servidor cortó un registro pero el panel siguió contando (red caída), al reconectar se extiende el registro cortado y se continúa en otro nuevo; queda marcado «a revisar» | No se pierden horas por cortes de wifi |
| 40 | Inactividad: al volver se pregunta (descontar y pausar / contar); el cuadro no se puede cerrar sin elegir | Pedido del usuario (2 h) |
| 41 | `Play.exe` se publica en un solo archivo autocontenido **sin comprimir** (~140 MB): comprimido pesa 63 MB pero usa ~60 MB más de RAM. Con GC no concurrente y sin PGO: ~80–95 MB privados. **NO usar `InvariantGlobalization`**: rompe toda escritura en cuadros de texto y PIN en WPF (error `CultureNotFoundException` por cada tecla con teclado es-AR); se descubrió en la primera prueba en otra PC (2026-11-18) | Priorizar memoria de un programa siempre abierto |
| 42 | El panel inicia con Windows (clave `HKCU\...\Run`, activada en la primera ejecución, se puede desactivar con clic derecho) y siempre arranca en pausa | Pedido del usuario |
| 43 | Programa de administración `PlayAdmin.exe` (WPF, `src/Play.Admin`), separado del panel y copiado a mano a las PCs de administradores (no se publica en la página de descarga de empleados). Ver `docs/ADMIN.md` | Pedido del usuario: administración como programa de escritorio aparte |
| 44 | Cliente de la API compartido en `Play.Client` (`ApiClient.LlamarAsync`, `AdminApi`), probado contra el servidor real | Evita duplicar y se puede probar sin ventanas |
| 45 | Las pruebas con UI real (`scripts/prueba-e2e-*.ps1`) usan UI Automation y **teclado real**: detectan problemas que las pruebas de lógica no ven (p. ej. el de `InvariantGlobalization`). Windows PowerShell 5.1 manda los acentos del cuerpo de un POST en otra codificación: usar bytes UTF-8 | Lecciones de la primera prueba en otra PC |
| 46 | El panel refresca usuarios y obras cada 30 s en silencio (`CargarListasAsync(tocarConexion: false)`) y, si arranca sin servidor, reintenta cada 4 s. Reabrir `Play.exe` con el panel ya abierto lo expande y refresca (evento con nombre). Refrescar al desplegar el menú se descartó (cerraba el menú) | Defecto encontrado por el usuario el 2026-11-18: el administrador creó un empleado y el panel abierto no lo mostraba |
| 47 | Con `--datos`, el nombre de mutex/evento usa un hash SHA-256 estable (`string.GetHashCode()` cambia en cada ejecución de .NET) | Un segundo panel de pruebas no detectaba al primero |
| 48 | «Eliminar registro» = marcar (`Anulado`) con motivo y constancia, recuperable; no borra de la base. Excluido de totales, Excel, resumen del empleado y solapamientos. No aplica a registros en curso | Pedido del usuario (2026-11-18); se eligió marcar y no borrar para no perder trazabilidad |
| 49 | La base se actualiza sola al arrancar el servidor (`Esquema.ActualizarAsync`: agrega columnas faltantes, idempotente, con copia previa `datos/backups/play-antes-de-actualizar-*.db`). Reemplaza a las migraciones de EF Core mientras los cambios sean solo columnas nuevas | Evita perder los datos de bases creadas por versiones anteriores |
| 50 | En la pestaña Registros los filtros buscan solos al cambiar (y siempre al entrar a la pestaña); solo vale la última búsqueda; la fila de filtros se acomoda en dos líneas si la ventana es angosta | El usuario creyó que los filtros «no funcionaban»: había que apretar Buscar |
| 51 | Actualización automática del panel (ver `docs/PANEL.md`): versión grabada en el .exe por el script de publicación, `GET /api/panel/version` (versión + SHA-256), descarga verificada en segundo plano, instalación solo sin registro en curso, reemplazo por **renombrado** (`.viejo`/`.nuevo`), confirmación de arranque de la nueva y vuelta atrás automática | Pedido del usuario: no tener que bajar el .exe en cada PC tras cada arreglo |
| 52 | Una versión con texto raro en el número (p. ej. los .exe de Microsoft: «10.0 (WinBuild…)») se ignora: solo se actualiza a versiones numéricas MÁS NUEVAS (nunca «hacia atrás») | Seguridad ante publicaciones equivocadas |
| 53 | Instancia única: «primera» es quien logra **tomar** el mutex (`new Mutex(false)` + `WaitOne(0)`), no quien lo crea (`createdNew`). Con `createdNew`, soltar el mutex no alcanza porque el objeto sigue existiendo mientras el proceso anterior tenga el handle: la copia nueva creía ser una segunda y se cerraba (rompía la actualización y el reinicio al cambiar de servidor, en el panel y en el administrador) | Defecto encontrado con la prueba real de actualización |
| 54 | La política de reinicio por actualización es una función pura probada (`PoliticaActualizacion`): nunca con el cronómetro andando; al abrir, sin usuario ≥30 s inactivo, o en pausa ≥2 min inactivo | El panel no debe cortarle el trabajo a nadie |
| 55 | Dos áreas, **Oficina** y **Taller**, solo para **empleados** (las obras son comunes). Empleados existentes → Oficina. El panel elige primero el área y luego el nombre; todos los administradores ven todo, con filtro por área. El Excel de horas trae «Área» y hoja «Por área» | Pedido de la usuaria (2026-11-19), respuestas a las preguntas de diseño |
| 56 | **PIN en texto legible** (`PinVisible`) para que el administrador los vea y exporte; el login sigue usando el hash. Cada consulta y cada exportación queda en la auditoría; los PIN se ocultan al salir de la pestaña. Los PIN elegidos antes de esta función no se conocen (hay que resetearlos). **Se descartó guardarlos cifrados (recomendado) por decisión de la usuaria.** Riesgo: quien obtenga la base o un backup ve todos los PIN | Pedido explícito de la usuaria; ver riesgos en `docs/ADMIN.md` |
| 57 | `Dialogos.Confirmar` del administrador usa una ventana propia (Sí/No) en vez del MessageBox nativo: mismo aspecto que el resto y automatizable con UI Automation | Pruebas con ventana real |
| 58 | **Subtareas** propias de cada obra (`Subtarea`: obra, nombre, activa; nombre único por obra). Se administran en la pestaña Obras; no se borran, se desactivan. No se separan por área | Pedido de la usuaria (2026-11-19), respuestas a las preguntas de diseño |
| 59 | Si la obra tiene al menos una subtarea **activa**, elegir una es **obligatoria** para Play y para cambiar de obra (el servidor devuelve `subtarea_requerida` / `subtarea_invalida`); si no tiene, el panel funciona como antes | Pedido de la usuaria |
| 60 | Cambiar de subtarea con el cronómetro andando = cambiar de obra: confirmación, cierra el registro y abre otro sin huecos. Al cambiar a una obra con subtareas, se elige en el mismo cuadro de confirmación | Pedido de la usuaria; un registro por tramo mantiene los totales simples |
| 61 | `sincronizar` (registros hechos sin conexión) **nunca rechaza por subtarea**: si falta o es inválida se guarda sin ella y queda «a revisar», porque las horas ya trabajadas no deben perderse | Misma filosofía que los solapamientos |
| 62 | El esquema se actualiza solo también con **tablas** nuevas (`Esquema.TablasNuevas`, además de columnas e índices); `Subtareas` se crea al arrancar el servidor, con copia previa | Las bases existentes no se tocaban con `EnsureCreated` |
| 63 | «Eliminar subtarea» = **terminarla (tachada)**, no borrarla: sigue en la lista del administrador, al final, tachada y en gris; deja de ser tarea pendiente y de ofrecerse a los empleados; las horas registradas se conservan; se puede reabrir | Aclaración de la usuaria (2026-11-19): «que no quede como tarea pendiente… que se vea tachada como una lista del súper». Un borrado real rompería el historial |
| 64 | Cualquier empleado puede avisar que terminó **cualquier** subtarea de la obra (no existe asignación empleado ↔ subtarea). El aviso **no termina nada**: queda «sin revisar» hasta que el administrador lo acepte (la tacha) o lo descarte | Respuestas de la usuaria; pendiente posible: asignar subtareas a empleados |
| 65 | Si se terminan todas las subtareas de una obra, esta vuelve a registrarse sin subtarea (la exigencia depende de que haya subtareas **pendientes**: activas y no terminadas) | Consecuencia de 59 y 63; propuesto y no objetado |
| 66 | El esquema se actualiza solo también con la tabla `AvisosSubtarea` y las columnas `Subtareas.Terminada/TerminadaUtc` (`Esquema`); `scripts/prueba-e2e-admin.ps1` ya no mata el administrador real del usuario (solo el proceso que abre) | Mantenimiento |
| 67 | Casilla **«Tarea terminada»** en el panel (en lugar de depender solo del menú): tildar = avisar al administrador, destildar = retirar el aviso sin revisar; la tarea **no** se tacha hasta que el administrador la acepta (decisión 64). Se mantiene también el menú «Avisar que terminé una subtarea…» para obras que no se están usando | Pedido de la usuaria (2026-11-19): «el empleado debería poder tener una casilla donde marcar si la tarea está hecha o no». Interpretación mía: la casilla avisa, no cierra por sí sola |
| 68 | **Horas de Taller**: el personal de Taller **reemplaza el cronómetro por «Cargar horas»** (no ve Obra ni Play). Una carga por empleado y día (`CargaHoras`, índice único parcial `Anulado = 0`), solo hoy o ayer, 1 min–24 h, sin obra. El servidor exige el área Taller (403 `solo_taller`). Play sigue permitido en el servidor para Taller (no se bloquea por compatibilidad), pero el panel no lo ofrece | Respuestas de la usuaria (reemplaza al cronómetro; fecha + horas, sin obra, hoy y ayer) |
| 69 | Corregir o agregar horas lo hace solo el administrador (motivo obligatorio, auditoría `horas_taller*`); tras eso el empleado **ya no puede** cambiar esa carga (`cargada_por_admin`). Eliminar = marcar (`Anulado`), recuperable; no se puede recuperar si ya hay otra carga vigente ese día | Misma filosofía que los registros de Play |
| 70 | Las horas de Taller **no se encolan sin conexión**: el panel avisa que no se guardaron y se repite con red. Es lo más simple y evita duplicados; si se necesita carga offline, habría que agregar cola local | Decisión mía, a confirmar con la usuaria |
| 71 | «Hoy» y «ayer» los fija el **servidor** (hora local del servidor), no la PC del empleado | Evita fechas manipuladas o relojes desfasados |
| 72 | **Las horas de Taller también figuran entre los registros** del administrador (Origen «carga», solo lectura; se corrigen en su pestaña) y en el Excel general (Origen «carga de horas», sin inicio/fin, obra «(Carga de horas)»). No se crean `RegistroTiempo` falsos: se combinan al consultar | Pedido de la usuaria (2026-11-19): «que las horas del taller queden registradas dentro de los registros, porque ellos también son empleados» |
| 73 | **Asistencia**: presente = Oficina con ≥1 registro de Play ese día (no eliminado, sin mínimo); Taller con ≥1 carga de horas (Play no cuenta para Taller). Solo lunes a viernes. Se cierra el día a las **23:59** (hora del servidor) y se genera **una falta por empleado y día** (`Faltas`, índice único). Sin faltas hacia atrás: el control empieza el día de la instalación (`Ajustes.asistencia_desde`), y para un empleado nuevo el día de su alta (`Empleado.CreadoFecha`). Un empleado de Taller que carga «ayer» hace desaparecer la falta | Respuestas de la usuaria (2026-11-19) |
| 74 | **Justificación**: la registra el administrador sin segunda aprobación; motivo obligatorio; quedan `Justificada` / `Injustificada` (revisada) / sin revisar (la alerta). «Dejarla injustificada» también quita una justificación. Todo en la Auditoría. Los empleados no ven la asistencia | Respuestas de la usuaria |
| 75 | **Feriados: no se implementan** (la usuaria pidió, el 2026-11-19, ignorarlos por completo y usar solo el sistema de justificación; antes había pedido cargarlos solos desde internet con la API `api.argentinadatos.com/v1/feriados/{año}`, ya probada). Un feriado se justifica como cualquier ausencia, con el motivo. Si se retoma: lista de feriados con carga automática, «puentes» desactivados por defecto y botón «marcar día como feriado» | Decisión de la usuaria |
| 76 | **Horas de Taller por obra y subtarea**: el personal de Taller elige obra y tarea y carga las horas de cada una (igual que Oficina con Play, pero a mano), y puede marcar la tarea como terminada con la casilla de aviso. Una **línea** = empleado + día + obra + subtarea; varias por día (≤ 24 h en total). La obra puede faltar («trabajo general de Taller»: es lo que ya había cargado antes y sirve para trabajo que no es de una obra). Se quita el índice único «una por día» (con migración automática) y se controla en código | Pedido de la usuaria (2026-11-19) |
| 77 | Las reglas de obra y subtarea de las horas de Taller son las de Play (obra activa; subtarea obligatoria si la obra tiene subtareas pendientes; una terminada ya no se ofrece). El **administrador** puede además cargar sobre una subtarea ya terminada o una obra inactiva | Misma coherencia que las correcciones de registros |
| 78 | El empleado puede **quitar** sus líneas de hoy o ayer (se marcan `Anulado`, no se borran); una línea que tocó el administrador ya no se puede cambiar ni quitar | Misma filosofía que 69 |
| 79 | **El Excel de empleados es la base de datos de empleados** (`Play:EmpleadosExcel`): columnas Empleado, Contraseña y Área (Oficina/Taller/Administrador). El servidor lo sincroniza solo cuando cambia (cada 10 s), con altas, bajas, PIN y área. «El Excel manda»: la app no edita nombre/PIN/área/estado de empleados y los empleados no cambian su PIN | Pedido de la usuaria (2026-11-20): «que la app se base en el siguiente excel… si se modifica algún pin o empleado se actualice» |
| 80 | **Primera sincronización = borrón y cuenta nueva** de los empleados: se eliminaron todos los empleados anteriores **y todo su rastro** (registros, horas de Taller, faltas, avisos, sesiones, constancias que los nombraban), con copia previa. Es una excepción a «no borrar usuarios» pedida expresamente por la usuaria («eliminar todo rastro de los empleados previos»). Después, quien deja de figurar se **desactiva** (no se borra) | Respuesta de la usuaria; los datos anteriores eran de prueba |
| 81 | El nombre (normalizado: sin espacios de más, sin distinguir mayúsculas) identifica a la persona: cambiarlo en el Excel = baja + alta. El PIN con apóstrofe o espacios se limpia (`0187'` → `0187`). Un PIN que no sean 4 números es un error de esa fila: se conserva el anterior y no se da de baja | Decisión mía a partir del Excel real |
| 82 | **Administradores desde el Excel**: las filas «Administrador» crean el administrador (usuario = nombre de pila con mayúscula inicial) con la contraseña del Excel como **temporal** (debe cambiarla). Si ya existía, solo se actualiza el nombre: su clave no se pisa y el Excel nunca los desactiva. Una persona puede ser empleada y administradora. La clave «la clave que figura en el Excel» del Excel es débil: se obliga a cambiarla | La usuaria pidió «crear los perfiles tal cual»; la clave temporal es mía por seguridad (si prefiere que la clave del Excel mande, es un cambio chico) |
| 83 | Si el Excel falta, está en uso, está vacío o roto, **no se cambia nada**; el estado y los errores por fila se muestran en Sistema y hay «Sincronizar ahora». La constancia en la Auditoría es del usuario «Sistema» y nunca lleva PIN | Para que un Excel mal guardado no deje sin acceso a nadie |
| 22 | PC servidor: **aún sin decidir**. Debe estar siempre encendida y con IP fija (reserva DHCP en el router) | Pendiente |
